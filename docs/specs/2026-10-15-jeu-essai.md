# Jeu d'essai du pipeline : spec

15 octobre 2026 · David (avec Claude) · à relire par Amos

## Le but

Faire passer **toujours la même donnée** dans le vrai Leon, comme chez un vrai client, pour savoir si un changement (consigne, modèle, seuil) l'améliore vraiment. Jusqu'ici, chaque essai tournait sur les sessions des derniers jours de David : on ne savait pas si un écart venait du changement ou de la donnée.

Critères de succès :
1. Une commande charge une entreprise fictive de 6 personnes et envoie ses conversations au serveur par la vraie API `ingest` ; le pipeline les traite sans intervention.
2. On se connecte à l'interface avec n'importe quel personnage et on lit sa mémoire comme un client.
3. Une commande note le résultat par rapport aux réponses attendues et ajoute une ligne à l'historique des essais, avec le coût mesuré par étape.
4. Rejouer le même jeu sur le même code donne des chiffres comparables ; les données réelles de la base locale ne sont jamais touchées.

## Le jeu de données

**L'entreprise** : « Atelier Numérique Lebrun » (fictive), 15 personnes, intégrateur de logiciels de gestion pour artisans du bâtiment. Elle a des clients, des fournisseurs, un produit, du code et de l'administratif.

**Les 6 personnages** (prénoms et adresses en `@essai.leon.local`) :

| Personnage | Rôle | Outils | Ce qu'il apporte |
|---|---|---|---|
| Claire | Dirigeante | claude.ai | décisions, recrutement, stratégie, salaires (sensible) |
| Karim | Commercial | ChatGPT | clients, devis, prix renégociés, concurrents |
| Hugo | Dev | Claude Code | longues sessions de code et de débogage, débats entre agents (`<teammate-message>`), recherches techniques ; calqué sur les sessions réelles de David |
| Inès | Dev (interface, mobile) | Claude Code, ChatGPT | sessions de code plus courtes, choix techniques qu'elle discute avec Hugo (mêmes décisions dites deux fois, parfois en désaccord), une bibliothèque abandonnée puis remplacée, un ticket client relayé par Karim |
| Sophie | Admin et finances | ChatGPT | fournisseurs, contrats, échéances, un arrêt maladie (sensible) |
| Nadia | Cheffe de projet | claude.ai, Claude Code | planning, engagements clients, dates qui glissent |

**Volume** : environ 60 conversations, environ 600 tours, étalés sur 3 semaines fictives (du 21/09 au 10/10/2026). Hugo et Inès pèsent ensemble à peu près la moitié des tours, comme les sessions de code dans les données réelles (672 tours, 16 sessions, tours de 1 100 caractères en moyenne, jusqu'à 11 500).

**Pièges voulus**, chacun présent plusieurs fois :
- **Bruit** : code, sorties d'outils, débogage sans décision, bavardage.
- **Même info, plusieurs voix** : un client et son interlocuteur cités par Karim, Nadia et Claire avec des formulations différentes (doublons à fusionner).
- **Info qui change** : un prix renégocié, une date de livraison décalée, un fournisseur remplacé (nouvelle valeur, l'ancienne n'est plus actuelle).
- **Contradictions** : deux personnes qui donnent deux valeurs différentes pour la même chose (conflit attendu).
- **Sensible** : salaires, santé, litige avec un salarié.
- **Secrets** : une fausse clé d'API et un mot de passe collés dans une session (masqués à la capture, jamais dans un fait).
- **Faux amis** : hypothèses, brouillons, questions générales (« c'est quoi le RGPD ? ») qui ne doivent pas devenir des faits.
- **Messages d'agents** : rapports de coéquipiers, qui ne sont pas du bruit.

**Fichiers** (`essai/`, à la racine) :
- `essai/entreprise.json` : l'organisation, les personnages, leur rôle.
- `essai/conversations/<personnage>/<AAAA-MM-JJ>-<sujet>.json` : une conversation au format exact de `IngestPayload` (`source` + `turns`), avec `external_id` stables.
- `essai/attendu/<même nom>.json` : pour chaque conversation, les faits que Leon doit retenir (énoncé de référence, fiche et type de fiche attendus, sensible ou non, tour d'origine), les faits qu'il ne doit pas retenir, les conflits et remplacements attendus.
- `essai/mini.json` : la liste d'une dizaine de conversations qui couvrent tous les pièges, pour un essai rapide.
- `essai/README.md` : comment lancer, le mot de passe commun des personnages, les pièges par conversation.

Les noms de fichiers sont en ASCII, en minuscules, avec des tirets. Toutes les données sont inventées : aucune donnée réelle, aucun vrai secret.

**Écriture** : rédigé dans une session Claude Code, avec des sous-agents par personnage, à partir d'une « bible » commune (clients, fournisseurs, projets, chronologie des événements) pour que les conversations se recoupent. Une relecture de cohérence vérifie les dates, les noms et que chaque fait attendu est bien dit dans le tour indiqué. Aucun appel API payant.

## Les commandes

Deux sous-commandes de la CLI existante (`src/cli/leon.ts`).

### `pnpm leon essai charger [--mini] [--label "…"]`

1. Vérifie que le serveur répond et qu'il tourne sur le commit courant : une route de santé `GET /api/v1/version` renvoie le commit du serveur, la commande refuse de lancer s'il diffère de `git rev-parse HEAD` (le piège du 14/10 : serveur non redémarré, passage facturé pour rien).
2. Affiche le nombre de tours et le coût estimé (d'après le dernier passage de l'historique, sinon 0,0022 $ par tour mesuré le 14/10), et demande confirmation.
3. Crée l'organisation et les 6 comptes s'ils n'existent pas (par le code d'inscription existant, `src/server/auth/sign-up.ts`), et un jeton d'API par personnage.
4. **Efface la mémoire de cette organisation seulement** (sources, tours, runs, faits, fiches, éléments à vérifier, usage), par une requête bornée à son `tenant_id`. Refuse si l'organisation n'a pas le nom d'essai attendu.
5. Envoie les conversations par `POST /api/v1/ingest`, avec le jeton de leur personnage, dans l'ordre chronologique global (par date du premier tour), par lots de 200 tours au plus.
6. Écrit `essai/.dernier-passage.json` (ignoré par Git) : identifiant du passage, libellé, commit, heure de début, runs créés.

### `pnpm leon essai noter`

1. Attend que tous les runs de l'organisation d'essai soient `done` ou `failed` (affiche l'avancement ; un run `failed` est compté et signalé, pas caché).
2. Lit, pour l'organisation d'essai : les faits actifs et en attente, leurs fiches, citations, sensibilité, conflits ; l'usage LLM par étape (table `llm_usage`, ci-dessous).
3. **Apparie** les faits produits aux faits attendus, conversation par conversation : un appel Haiku par conversation reçoit les deux listes et renvoie les paires ; une fonction pure n'accepte que des identifiants présents dans les listes. Coût estimé : ~0,03 $ par passage.
4. Calcule la note sans LLM :
   - **rappel** : faits attendus retrouvés / faits attendus ;
   - **précision** : faits produits appariés / faits produits ;
   - **faux faits** : faits produits qui correspondent à un « ne pas retenir » ;
   - **citations exactes** : faits dont la citation est vérifiée ;
   - **fiches correctes** : faits appariés rangés dans la fiche attendue ;
   - **doublons** : fiches ou faits en double là où un seul est attendu ;
   - **conflits et remplacements** trouvés / attendus ;
   - **sensible** : faits sensibles attendus marqués sensibles, et aucun sensible partagé ;
   - **secrets** : aucun faux secret présent dans un fait (recherche exacte).
5. Ajoute le résultat à l'historique et affiche un résumé comparé au passage précédent.

`--mini` restreint aux conversations de `essai/mini.json` (~100 tours, ~0,25 $ estimé).

## Le coût mesuré : table `llm_usage`

Aujourd'hui, le coût de chaque appel n'est écrit que dans la console (`logUsage`, `src/server/llm/anthropic-llm.ts`), sans organisation ni run. On l'enregistre aussi en base :

```sql
create table llm_usage (
  id uuid primary key default gen_random_uuid(),
  tenant_id uuid not null references organization(id) on delete cascade,
  ingest_run_id uuid,
  step text not null check (step in ('triage','extraction','placement','essai_juge')),
  model text not null,
  input_tokens integer not null, output_tokens integer not null,
  cache_read_tokens integer not null, cache_write_tokens integer not null,
  cost_usd numeric(12,6),
  created_at timestamptz not null default now()
);
```

- RLS par `tenant_id` ; lecture réservée aux administrateurs de l'organisation (pas d'interface en V1).
- `LlmRequest` gagne `tenantId` et `ingestRunId`, que les étapes connaissent déjà par le job ; l'écriture se fait après chaque appel, et un échec d'écriture est journalisé sans faire échouer l'étape.
- Le journal console reste tel quel.
- Utile au-delà de l'essai : savoir ce que coûte chaque client.

## L'historique des essais

- `docs/etudes/essais-pipeline/historique.md` : un tableau, une ligne par passage noté : date, libellé, commit, jeu (complet ou mini), modèles par étape, coût par étape et total, tokens, durée, et les notes ci-dessus.
- `docs/etudes/essais-pipeline/passages/<AAAA-MM-JJ-HHMM>-<libelle>.json` : le détail (notes par conversation, faits manqués, faux faits, appariements) pour comprendre un écart.
- Les deux sont commités : Amos voit les mêmes chiffres. Chaque chiffre est étiqueté « mesuré ».

## Hors champ

- Pas d'évaluation du MCP, du briefing ni de la recherche (on les essaie à la main dans l'interface et Claude Code).
- Pas de lancement automatique en CI : chaque passage coûte de l'argent.
- Pas de second jeu sur données réelles.
- Pas d'interface pour l'historique ni pour `llm_usage`.

## Les PR

1. **`llm_usage`** : migration `0007`, écriture après chaque appel, tests (écriture, RLS, échec d'écriture non bloquant). Petite et utile seule.
2. **Jeu d'essai** : `essai/`, route de version, sous-commandes `essai charger` et `essai noter`, historique. Tests : effacement borné à l'organisation d'essai, appariement (identifiants inventés rejetés), calcul des notes sur un cas fabriqué, refus si le commit du serveur diffère.
3. **Premier passage de référence**, noté et inscrit dans l'historique (~1,30 $ estimé, annoncé avant).

## Risques

- **Le jeu est trop facile ou trop artificiel** : les conversations écrites pour l'occasion sont plus propres que les vraies. Parade : calquer les sessions de Hugo et Inès sur la structure des sessions réelles (longueur, bruit, messages d'agents) et garder un œil sur l'écart avec les passages réels.
- **Le juge se trompe** : l'appariement Haiku peut rater ou inventer une paire. Parade : le détail des appariements est dans le JSON du passage, et la fonction pure rejette les identifiants hors liste.
- **Variabilité** : deux passages identiques ne donnent pas exactement la même note. À mesurer au premier passage en relançant une fois le mini.
- **Effacement** : un bug pourrait effacer la mauvaise organisation. Parade : requête bornée au `tenant_id`, vérification du nom, test dédié.
